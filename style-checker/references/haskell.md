# Google Haskell Style Guide — Formatting & Naming

Source: https://google.github.io/styleguide/haskellguide.html

Google publishes this Haskell guide. Use it, not community guides such as Johan Tibell's or formatter defaults such as Ormolu and Fourmolu, which differ on several points (indent width, blank lines after imports, comma spacing in tuples).

## File Structure

### Pragmas
- `OPTIONS_GHC` and `LANGUAGE` pragmas go at the **very top** of the file.
- **At most one `{-# OPTIONS_GHC ... #-}`, first.** Use it only for options specific to the file (such as `-fno-warn-orphans` in tests). General options like `-O2` belong in the `.cabal` file.
- Then **one `{-# LANGUAGE ... #-}` per extension**, in **sorted order**. `{-# LANGUAGE OverloadedStrings, TupleSections #-}` is wrong.
- Extensions are listed in every file that needs them, never enabled globally in the `.cabal` file.
- Use only these non-controversial extensions; avoid all others:
  `BangPatterns`, `CPP`, `DeriveDataTypeable`, `DeriveFoldable`, `DeriveFunctor`, `DeriveGeneric`, `DeriveTraversable`, `DisambiguateRecordFields`, `FlexibleContexts`, `ForeignFunctionInterface`, `GADTs`, `GeneralizedNewtypeDeriving`, `MagicHash`, `MultiParamTypeClasses`, `NamedFieldPuns`, `OverloadedStrings`, `PatternGuards`, `Rank2Types`, `RankNTypes`, `RecordWildCards`, `ScopedTypeVariables`, `TemplateHaskell`, `TupleSections`, `TypeFamilies`, `ViewPatterns`.
- `INLINE` / `INLINEABLE` only when measured to help, placed directly after the declaration.

### Module Header and Exports
- Every module has an **explicit export list** (exception: most exports generated by Template Haskell).
- The export list starts on a new line after `module`, in leading-comma list format. Related exports may share a line. Order tells a story; it is the Haddock order.
- Do not re-export modules for convenience. Allowed: re-exporting from `Internal` modules, and a package module that only re-exports the package's common modules.

```haskell
module RunLength
    ( RunList
    , rleEncode
    , rleDecode
    ) where
```

### Imports
- Imports may be split into groups separated by one blank line. Recommended: external modules, then internal modules.
- **Within each group, alphabetize by full module name.**
- Import either qualified or with an explicit import list (or both).
- Importing a module wholesale (no list, not qualified) is acceptable for modules designed for it, such as `Data.Bits`. For modules from the same package it is allowed but discouraged.
- The qualified name is the **last component** of the module name (`import qualified Data.Ratio as Ratio`). Related modules may share a name (`Data.Text` and `Data.Text.IO` as `T`).
- These short qualified names are allowed:

```haskell
import qualified Data.ByteString as BS
import qualified Data.ByteString.Lazy as BL
import qualified Data.HashMap.Strict as HM
import qualified Data.HashSet as HS
import qualified Data.Map as M
import qualified Data.Set as S
import qualified Data.Text as T
import qualified Data.Text.Lazy as TL
```

Any other abbreviation (such as `Txt`) is wrong.

### Warnings
- Code compiles cleanly with `-Wall` and `-Werror`. Suppress orphan warnings only with `{-# OPTIONS_GHC -fno-warn-orphans #-}` at the top of the file that needs it.

## Naming

- **Mixed case, no underscores**: `orderTotal`, not `order_total`. The compiler enforces type vs value capitalization.
- Underscores are allowed only for:
  - an unused argument or pattern: `_`, or `_sizeHint` when a name helps;
  - QuickCheck properties, tests, test groups, and test modules: `prop_UnionIsAssociative`, `test_SetOperations`, `Data.MultiWaySet_Test`;
  - a name that would otherwise be a reserved word: `type_`.
- Tick marks for altered values are idiomatic: `fib`, `fib'`.
- Lists use plurals: `(a:as)`.
- **Short and single-letter names are encouraged** when the scope is a few lines: `nextAfter m (x:y:ys)`.
- **Modules are singular**: `Data.Map`, not `Data.Maps`.
- **Abbreviations are mixed case**: `HttpResponse`, `IpBlock`, `parseHttpLine` — not `HTTPResponse`. Exception: a form with strong specific precedent (`GREoIPsec`). Ordinary all-caps abbreviations like `HTTP` are not an exception.

## Formatting

### Layout
- Use **layout**, not braces and semicolons, except for one-liners.

### Line Length and Whitespace
- **80 columns.** No trailing spaces. No tabs.
- Horizontal alignment that shows structure is **acceptable and encouraged**: aligned `=`, `->`, `|`, and `::`.

### Indentation
- **Indents are on 4-space intervals.** 2-space indentation is wrong (except the hanging `where`, below).
- A continued expression is indented one level from the line before it, not from the construct it continues.

### Vertical Spacing
- One blank line separates top-level declarations.
- **Two blank lines** between the imports and the first top-level declaration, and between major sections of a file. One blank line there is wrong.
- No blank lines are required between declarations inside a `where`.

### Lists, Records, Exports, Imports: Leading Commas
- A list, record declaration, record value, export list, or import list that spans several lines uses **leading commas**: each following line starts with `,`, and the closing bracket is on its own line.
- Several logically grouped items may share a line, separated by `, `.

```haskell
exceptions =
    [ InvalidStatusCode
    , MissingContentHeader
    , InternalServerError
    ]

data Person = Person
    { firstName :: !String  -- ^ First name
    , lastName  :: !String  -- ^ Last name
    , age       :: !Int     -- ^ Age
    } deriving (Eq, Show)
```

Trailing-comma style (`{ firstName :: String,`) is wrong.

### Data Declarations and `deriving`
- Alternatives align under `=` or start on new lines with leading `|`.
- `deriving` may trail the declaration or sit on its own line.

```haskell
data Tree a = Branch a (Tree a) (Tree a)
            | Leaf

data HttpException
    = InvalidStatusCode Int
    | MissingContentHeader
    deriving (Eq, Show)
```

### `where`
- For local declarations, use a **hanging `where`**: `where` on its own line indented 2 spaces, the declarations indented 4.
- For `module`, `class`, and `instance` declarations, use a trailing `where`.

```haskell
rleEncode (a:as) = go 1 a as
  where
    go n a [] = [(n,a)]
```

`f x = g y where` followed by the local declarations is wrong for local declarations.

### `case ... of`
- `of` on the **same line** as `case`. Cases indented. Align `->` when it helps.

### `let ... in`
- `in` on the line after `let`, **lined up with `let`**. A short `let` may be on one line.

```haskell
access add = let (s,a) = add `divMod` segmentSize
                 (p,b) = a `divMod` pageSize
             in getPageByte b . getSegmentPage p <$> getSegment s
```

### `if ... then ... else`
- `then` and `else` are indented one level from the **line containing the `if`**, not from the `if` itself. The same applies to nested `do` blocks.
- A short expression may be on one line: `adjective n = if odd n then "odd" else "even"`.
- Prefer guards and pattern matches over nested `if` at the outer level of a function. Report a nested `if` chain as Low.

### Operators and Punctuation
- One space around every operator, including backticked functions (`` x `mod` 10 ``).
- One space after commas and semicolons.
- **No space after a lambda backslash**: `\s -> ...`, not `\ s -> ...`.
- Operator sections: **no space on the unapplied side**: `(++ " likes noodles")`, `(* 2)`. `( * 2)` is wrong.
- Exception: for tuples and common single-character operations, the space after a comma or around an operator may be dropped when it reads better: `swap (a,b) = (b,a)`, `10*v + digitToInt d`, `go (n+1)`. Do not report these.

## Comments and Haddock

- Use `--` for all comments, except pragmas or a comment in the middle of a line.
- **At least two spaces** between code and an end-of-line `--`, and one space after `--` when text follows.
- The **module and every exported top-level element have Haddock** (`-- |`), directly before the element, in proper sentences. Without an export list, every top-level element is exported.
- Exception: very simple type synonyms and very obvious declarations need no Haddock (`type Forest p a = [Tree p a]`).
- Haddock need not repeat argument names or types. Links only for the first occurrence of an API name a reader may want to follow.
- Comments in code explain non-obvious reasons, not the implementation.
- Align end-of-line comments on record fields.

---

## Types and Idioms

- **Every top-level function has a type signature.** Use the most polymorphic reasonable type.
- **Avoid partial functions** from the Prelude and base: `head`, `(!!)`, `minimum`, `fromJust`, `read`. Allowed when nearby pattern matching or logic makes the call safe. Do not write partial functions; `error` is acceptable only for cases a module's own invariants make unreachable.
- Point-free style is fine, but not contorted: `f = (g .) . h` is wrong; write `f x = g . h x`.
- Tests use QuickCheck where possible, HUnit for special cases. `Arbitrary` instances go in the matching `_Test` module.
